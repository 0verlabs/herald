# x402: technical brief for an any-asset, cross-chain gateway

Research date: snapshot of docs.x402.org `llms-full.txt` (read in full) plus the spec and SDK source in `x402-foundation/x402` at commit `9843d75`. Content was rephrased for compliance with licensing restrictions; JSON examples below are illustrative shapes written for this brief, using the field names from the spec.

Repository note: the docs and specs now live at [github.com/x402-foundation/x402](https://github.com/x402-foundation/x402). `github.com/coinbase/x402` is listed by GitHub as a fork of it. Go import paths are `github.com/x402-foundation/x402/go/v2`.

Question this brief answers: can an "x402 gateway" that lets a buyer pay in any asset on any chain, with settlement to the provider through NEAR Intents, fit inside the existing protocol, or does it need a new scheme?

---

## 1. Request flow

### 1.1 Sequence (v2, default `authorization` payment flow)

1. Client sends a normal request.
2. Server answers `402 Payment Required` with a `PAYMENT-REQUIRED` header holding a base64-encoded JSON `PaymentRequired` object. In v2 the header is the canonical location; the body is an implementation concern. ([HTTP transport v2](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md))
3. Client picks one entry from `accepts`, builds a `PaymentPayload` for that entry's `scheme` + `network`, and retries with a `PAYMENT-SIGNATURE` header (base64 JSON).
4. Server verifies, locally or via facilitator `POST /verify`.
5. Server runs the handler.
6. Server settles, locally or via facilitator `POST /settle`. The facilitator broadcasts and waits for confirmation.
7. Server replies with a `PAYMENT-RESPONSE` header (base64 `SettlementResponse`). Success is `200` with the resource; failure is `402` with error details. ([Facilitator](https://docs.x402.org/core-concepts/facilitator), [Client/Server](https://docs.x402.org/core-concepts/client-server))

### 1.2 Header names by version

| Purpose | v1 | v2 |
| - | - | - |
| Requirements (server → client) | JSON body of the 402 (`PaymentRequirementsResponse`) | `PAYMENT-REQUIRED` header (base64 `PaymentRequired`) |
| Payment (client → server) | `X-PAYMENT` | `PAYMENT-SIGNATURE` |
| Settlement result (server → client) | `X-PAYMENT-RESPONSE` | `PAYMENT-RESPONSE` |
| Extension outcomes (facilitator sidechannel) | n/a | `EXTENSION-RESPONSES` (base64 JSON keyed by extension) |
| Sign-in proof (SIWX extension) | n/a | `SIGN-IN-WITH-X` |

Sources: [transports-v1/http.md](https://github.com/x402-foundation/x402/blob/main/specs/transports-v1/http.md), [transports-v2/http.md](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md), [Migration v1→v2](https://docs.x402.org/guides/migration-v1-to-v2), [HTTP 402](https://docs.x402.org/core-concepts/http-402). None of the headers are CORS-safelisted; browser-facing servers must expose/allow them explicitly (transport v2 spec, "Browser clients").

HTTP status mapping: 402 payment required or payment failed; 400 malformed payload; 500 server error; 200 success. A Permit2 payer with no allowance gets `412` / `permit2_allowance_required`.

### 1.3 `PaymentRequired` (v2)

Fields ([spec v2 §5.1](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md)):

| Field | Required | Notes |
| - | - | - |
| `x402Version` | yes | `2` |
| `error` | no | human-readable reason |
| `resource` | yes | `ResourceInfo`: `url` (req), `description`, `mimeType`, `serviceName` (≤32 ASCII), `tags` (≤5), `iconUrl` |
| `accepts` | yes | array of `PaymentRequirements` |
| `extensions` | no | map of extension key → `{ info, schema }` |

Each `PaymentRequirements` entry:

| Field | Required | Notes |
| - | - | - |
| `scheme` | yes | e.g. `exact`, `upto`, `batch-settlement`, `auth-capture` |
| `network` | yes | CAIP-2, e.g. `eip155:8453` |
| `amount` | yes | atomic units, string. (v1 called this `maxAmountRequired`.) |
| `asset` | yes | token address / mint / contract id. Spec also allows an ISO 4217 code for fiat |
| `payTo` | yes | recipient address, or a role constant such as `"merchant"` |
| `maxTimeoutSeconds` | yes | time budget for completing the payment |
| `extra` | no | scheme-specific; protocol-reserved keys `assetTransferMethod` and `paymentFlow` |

Illustrative multi-chain 402 (decoded header):

```json
{
  "x402Version": 2,
  "resource": { "url": "https://api.example.com/quote", "mimeType": "application/json" },
  "accepts": [
    { "scheme": "exact", "network": "eip155:8453", "amount": "10000",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913", "payTo": "0xSellerOnBase",
      "maxTimeoutSeconds": 60, "extra": { "name": "USD Coin", "version": "2" } },
    { "scheme": "exact", "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp", "amount": "10000",
      "asset": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v", "payTo": "SellerSolanaPubkey",
      "maxTimeoutSeconds": 60, "extra": { "feePayer": "FacilitatorFeePayerPubkey" } },
    { "scheme": "exact", "network": "near:mainnet", "amount": "10000",
      "asset": "17208628f84f5d6ad33f0da3bbbeb27ffcb398eac501a31bd6ad2011e36133a1",
      "payTo": "seller.near", "maxTimeoutSeconds": 60 }
  ]
}
```

v1 differences: requirements carried `resource`, `description`, `mimeType`, `outputSchema` inside each `accepts` entry; networks were strings like `base-sepolia`; no `resource` object and no `extensions` ([spec v1](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v1.md)).

### 1.4 The `accepts` array and how the client picks

- A server can list many entries, each with its own `scheme`, `network`, `asset`, `amount`, and `payTo`. The seller quickstart and exact docs show one route accepting Base, Solana, and Algorand together ([Quickstart for Sellers](https://docs.x402.org/getting-started/quickstart-for-sellers), [Exact](https://docs.x402.org/schemes/exact)).
- The protocol leaves selection to the client. The TypeScript SDK (`x402Client.selectPaymentRequirements`, `typescript/packages/core/src/client/x402Client.ts` ~L777-847) does, in order:
  1. keep entries whose `scheme`/`network` match a scheme the client registered (e.g. `client.register("eip155:*", new ExactEvmScheme(signer))`);
  2. drop entries whose `extra.paymentFlow` is not `authorization`, `upfront`, or `escrow`;
  3. apply **spend controls**: by default only recognized USD-pegged default assets are payable and each payment is capped at **$1**; other tokens need `allowedAssets` opt-in ([Quickstart for Buyers → Spend Controls](https://docs.x402.org/getting-started/quickstart-for-buyers));
  4. run user policies;
  5. prefer `authorization` flow entries over pre-handler-settlement flows;
  6. call the selector, default `accepts[0]`, so **server order is the tie-breaker** ([MCP guide](https://docs.x402.org/guides/mcp-server-with-x402) also says the default is server-ordered `accepts[0]`).

### 1.5 `PaymentPayload` (v2)

| Field | Required | Notes |
| - | - | - |
| `x402Version` | yes | |
| `resource` | no | `ResourceInfo` |
| `accepted` | yes | the chosen `PaymentRequirements`, echoed |
| `payload` | yes | scheme/network-specific (see §2) |
| `extensions` | no | client echoes server-declared extension `info`; may add, must not delete or overwrite |

v1 payload was `{ x402Version, scheme, network, payload }` with no `accepted` echo.

Server-side matching: the v2 TS resource server accepts a payload only if `accepted` deep-equals one of the requirements it advertises for that request (additive keys in `extra` and scheme-declared dynamic fields excepted) (`findMatchingRequirements` / `paymentRequirementsMatchAccepted` in `typescript/packages/core/src/server/x402ResourceServer.ts` ~L1390, ~L2330). v1 matched only on `scheme` + `network`.

### 1.6 `SettlementResponse` and `VerifyResponse`

`SettlementResponse` (`PAYMENT-RESPONSE` header, and `/settle` body): `success` (req), `errorReason`, `errorMessage`, `payer`, `transaction` (req; empty if nothing broadcast), `network` (req), `amount` (actual settled, e.g. for `upto`), `extensions`.

`VerifyResponse` (`/verify` body): `isValid` (req), `invalidReason`, `invalidMessage`, `payer`, `extensions`, `extra`.

`settlement_pending` is a non-terminal `errorReason`: the tx was broadcast but confirmation was not observed. It must carry a non-empty `transaction` hash. The TS resource server retries settle once; the facilitator reconciles via a `PendingSettlementStore` instead of re-broadcasting ([Facilitator → Settlement pending](https://docs.x402.org/core-concepts/facilitator), spec v2 §9).

## 2. Schemes and networks

### 2.1 Scheme catalogue

| Scheme | Semantics | Payment flows | Where |
| - | - | - | - |
| `exact` | pay exactly `amount` | `authorization` (default), `upfront` | all networks |
| `upto` | sign for a ceiling, server settles actual usage via `setSettlementOverrides` (atomic, `"50%"`, or `"$0.05"`; `"0"` = no charge) | `authorization` only | EVM (Permit2), SVM (payment-channels program) |
| `batch-settlement` | deposit once into escrow/channel, per-request cumulative vouchers, seller claims in batches later | `authorization` | EVM, SVM |
| `auth-capture` | authorize/hold, then capture, void, refund; client can reclaim after deadline | `escrow` (default), `authorization` | EVM (TS, Go) |

Sources: [Schemes overview](https://docs.x402.org/schemes/overview), [Upto](https://docs.x402.org/schemes/upto), [Batch settlement](https://docs.x402.org/schemes/batch-settlement), [auth-capture spec](https://github.com/x402-foundation/x402/blob/main/specs/schemes/auth-capture/scheme_auth_capture.md), [SDK Features](https://docs.x402.org/sdk-features). There is no scheme named `deferred`; `batch-settlement` is the deferred-redemption scheme. A `batch-settlement` Cloudflare binding uses `payTo: "merchant"` as a role constant ([spec](https://github.com/x402-foundation/x402/blob/main/specs/schemes/batch-settlement/scheme_batch_settlement_cloudflare.md)).

Payment flows (spec v2 §6.1): `authorization` = verify → handler → settle → respond; `upfront` = settle → handler → respond (no `/verify`); `escrow` = settle → handler → settle → respond. When the flow is not `authorization`, `accepts[].extra.paymentFlow` must say so. Clients must skip flows they do not recognize.

### 2.2 `exact` on EVM

From [scheme_exact_evm.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_evm.md):

- **`eip3009`** (default when `extra.assetTransferMethod` is absent). Client signs EIP-712 `TransferWithAuthorization`. `extra.name` / `extra.version` (token EIP-712 domain) are required. Payload:
  ```json
  { "signature": "0x…65 bytes",
    "authorization": { "from": "0xPayer", "to": "0xPayTo", "value": "10000",
                       "validAfter": "0", "validBefore": "1740672154", "nonce": "0x…32 bytes" } }
  ```
  Facilitator checks signature, balance, amount, time window, token/network, simulates, then calls `transferWithAuthorization`. The TS client sets `validAfter = 0` and `validBefore = now + maxTimeoutSeconds` (`mechanisms/evm/src/exact/client/eip3009.ts` L28-29).
- **`permit2`** (any ERC-20). Client signs `permitWitnessTransferFrom` with `spender` = canonical `x402ExactPermit2Proxy` and a witness `{ to, validAfter }`; the proxy only sends to `witness.to`. Payload key is `permit2Authorization` (`permitted.token`, `permitted.amount`, `from`, `spender`, `nonce`, `deadline`, `witness`). Needs a one-time Permit2 allowance; the `eip2612GasSponsoring` and `erc20ApprovalGasSponsoring` extensions make that gasless.
- **`erc7710`** (smart-account delegations).
- In all methods the facilitator cannot change amount or destination; it only broadcasts. Facilitator pays gas.
- Wallet-type caveats (EOA, ERC-4337, ERC-6492 counterfactual, EIP-7702) per method: [Wallet Compatibility](https://docs.x402.org/advanced-concepts/wallet-compatibility).

### 2.3 `exact` on Solana (SVM)

From [scheme_exact_svm.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_svm.md):

- `extra.feePayer` names the sponsor (facilitator or merchant); optional `extra.memo` (seller-defined, used as Memo data), `extra.recentBlockhash`, `extra.ataCreationRequired`.
- Client builds a `TransferChecked` (SPL or Token-2022) transaction, partially signs it, sends `{ "transaction": "<base64>" }`. The sponsor adds the fee-payer signature and submits.
- Exactly one matching transfer to the ATA derived from `payTo` + `asset`; overpayment tolerated, underpayment not.
- Optional `extra.splits` (multi-payee: platform fee, revenue share) is fully specified only for SVM ([scheme_exact.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact.md)).
- Duplicate-settlement race: facilitators keep a `SettlementCache` (120 s). Self-settling servers must implement their own ([Client/Server](https://docs.x402.org/core-concepts/client-server)).

### 2.4 Other networks

`exact` network bindings exist for EVM, SVM, AVM (Algorand), Stellar, Aptos, Casper, Hedera, TON, Canton, Cardano, Keeta, Sui, Concordium, NEAR, XRPL, Starknet (spec file present), and Bitcoin Lightning (`lnbtc`) ([Exact](https://docs.x402.org/schemes/exact), [`specs/schemes/exact/`](https://github.com/x402-foundation/x402/tree/main/specs/schemes/exact)). Fee payer varies: facilitator-sponsored on EVM/SVM/NEAR/Stellar; payer-paid on XRPL and Cardano.

CAIP-2 identifiers ([Networks & Token Support](https://docs.x402.org/core-concepts/network-and-token-support)):

| Family | Format / examples |
| - | - |
| EVM | `eip155:<chainId>`, any chain (e.g. `eip155:8453` Base, `eip155:1`, `eip155:137`, `eip155:42161`, `eip155:43114`) |
| Solana | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` (mainnet), `solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1` (devnet) |
| TON | `tvm:-239`, `tvm:-3` |
| Algorand | `algorand:wGHE2Pwdvd7S12BL5FaOP20EGYesN73k` |
| Stellar | `stellar:pubnet`, `stellar:testnet` |
| Aptos | `aptos:1`, `aptos:2` |
| Hedera | `hedera:mainnet`, `hedera:testnet` |
| Keeta | `keeta:21378` |
| **NEAR** | **`near:mainnet`, `near:testnet`** |
| Canton | `canton:mainnet` (synchronizer id in `extra.synchronizerId`) |
| Concordium | `ccd:<genesisHash>` |
| XRPL | `xrpl:0`, `xrpl:1` |
| Cardano | `cardano:mainnet`, `cardano:preprod` |
| Sui | `sui:mainnet` |
| Casper | `casper:casper-test` (from exact docs) |

Non-blockchain rails are encouraged to use CAIP-2 style too (e.g. `ach:us`), per spec v2 §11.1.

Facilitators support networks, not specific tokens. Any ERC-20 works on EVM via EIP-3009 or Permit2; dollar-string prices (`"$0.01"`) only work where a default stablecoin is configured, otherwise use an explicit `{ amount, asset }` TokenAmount ([Networks & Token Support](https://docs.x402.org/core-concepts/network-and-token-support)).

### 2.5 NEAR specifically

Yes, NEAR is supported ([scheme_exact_near.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_near.md)):

- v2 only; `near:mainnet` / `near:testnet`; asset = NEP-141 contract account id; `payTo` = NEAR account id; no required `extra`.
- Payload: `{ "signedDelegateAction": "<base64 Borsh NEP-366 SignedDelegateAction>" }`.
- The delegate action must contain **exactly one `FunctionCall` to `ft_transfer`** with `receiver_id == payTo`, `amount == amount`, deposit exactly 1 yoctoNEAR. `ft_transfer_call` and extra actions are rejected. Full-access keys only.
- Relayer (facilitator) pays gas and the 1 yocto; payer spends only the token.
- Expiry: `max_block_height = current + ceil(maxTimeoutSeconds / 1s)`; replay via on-chain access-key nonce.
- Preflight requires `storage_balance_of(payTo)` to be non-null when the token implements NEP-145, so the recipient must be storage-registered.
- Settlement waits for the inner `ft_transfer` receipt to finish (`wait_until: FINAL`) before `success: true`.
- SDK: TypeScript only, package `@x402/near` (`ExactNearScheme`, `createClientNearSigner`) ([SDK Features](https://docs.x402.org/sdk-features)).
- Facilitators listing NEAR: "NEAR x402 Facilitator" (x402.mikedotexe.com, NEAR + Base, USDC) and Solvador ([Facilitators](https://docs.x402.org/dev-tools/facilitators)). The public x402.org facilitator does not list NEAR; issue [#2812](https://github.com/x402-foundation/x402/issues/2812) asks for NEAR testnet registration.
- Nothing in the docs or specs mentions NEAR Intents, `intents.near`, or 1Click.

## 3. The facilitator

Role: verify payloads and submit settlement transactions; it does not custody funds ([Facilitator](https://docs.x402.org/core-concepts/facilitator)). It is optional: a server can verify and settle itself ("self-facilitate").

### 3.1 Endpoints (spec v2 §7)

`POST /verify`: read-only, must not write chain state.

```json
{ "x402Version": 2, "paymentPayload": { /* PaymentPayload */ }, "paymentRequirements": { /* PaymentRequirements */ } }
```
→ `{ "isValid": true, "payer": "0x…" }` or `{ "isValid": false, "invalidReason": "insufficient_funds", "payer": "0x…" }`.

`POST /settle`: same request body. → `{ "success": true, "payer": "…", "transaction": "0x…", "network": "eip155:8453" }`, or `success: false` with `errorReason` and `transaction: ""`. Settle may run more than once per payment (escrow flow); for `upto`, `paymentRequirements.amount` at settle time means the amount to charge.

`GET /supported`:

```json
{ "kinds": [ { "x402Version": 2, "scheme": "exact", "network": "eip155:8453", "extra": {} } ],
  "extensions": ["bazaar"],
  "signers": { "eip155:*": ["0xFacilitatorSigner"], "solana:*": ["FeePayerPubkey"] } }
```

`kinds[].extra` carries scheme config (e.g. SVM `feePayer`, `transactionVersions`; batch `receiverAuthorizer`; split limits). Optional Bazaar endpoints: `GET /discovery/resources`, `GET /discovery/search`.

v1 had the same three endpoints with v1 payload shapes and a `/supported` that listed only `kinds`.

### 3.2 Gas

Facilitator pays gas on EVM `exact`/`upto` (both methods are "gasless" for the payer), Solana (fee payer), NEAR (relayer), Stellar (sponsored). Payer pays on XRPL and Cardano. Running a facilitator requires a wallet funded with native gas per network ([Networks & Token Support → Running Your Own Facilitator](https://docs.x402.org/core-concepts/network-and-token-support)).

### 3.3 Custom / third-party facilitators

Permissionless: anyone can run one ([FAQ](https://docs.x402.org/faq), [Facilitators](https://docs.x402.org/dev-tools/facilitators)). SDKs ship facilitator classes (`x402Facilitator` in `@x402/core/facilitator`, Go, Python) with hooks (`onBeforeVerify`, `onAfterSettle`, …). A server points at any facilitator via `new HTTPFacilitatorClient({ url, timeoutMs })` (default timeout 90 s).

Known facilitators (docs list, not exhaustive): x402.org (testnet only: Base Sepolia, Solana devnet, Stellar/Aptos/Hedera/XRPL testnets), CDP (Coinbase, `https://api.cdp.coinbase.com/platform/v2/x402`, KYT/OFAC), PayAI (`https://facilitator.payai.network`), AlgoVoi, Built on Stellar, Celo, Corbits, Dexter, Fireblocks, FTP Canton, HPP, Meridian, Mogami, NEAR x402 Facilitator, Polygon, Solvador, Sui (UIG Studios), T54 XRPL, X Pay, TRDEFI Arc.

## 4. Extensibility

### 4.1 New scheme or network binding

- Process ([specs/CONTRIBUTING.md](https://github.com/x402-foundation/x402/blob/main/specs/CONTRIBUTING.md)): open an issue/discussion explaining why existing schemes do not suffice, then write `specs/schemes/<name>/scheme_<name>.md` (from [`scheme_template.md`](https://github.com/x402-foundation/x402/blob/main/specs/scheme_template.md): Summary, Use Cases) and one `scheme_<name>_<network>.md` per network (from [`scheme_impl_template.md`](https://github.com/x402-foundation/x402/blob/main/specs/scheme_impl_template.md): Payment payload, Verification, Settlement). Schemes must cover replay prevention, authorization scope, settlement atomicity.
- Inside `exact`, new **asset transfer methods** can be added per network via `extra.assetTransferMethod`. [scheme_exact.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact.md) defines two method families:
  - **Facilitator-submitted**: client signs, facilitator submits. Must declare fee payer, replay primitive, validity window, duplicate-submission behavior; must produce one identifiable transfer of `amount` of `asset` to `payTo`.
  - **Client-submitted (payment proof)**: client submits the payment itself and presents a proof; settle validates and binds it to the request. The spec explicitly covers the case where the client's payment kicks off asynchronous downstream settlement. Must use `upfront`. Requires: instrument advertised in requirements (e.g. a per-payment recipient address in `payTo`, or in `extra`), request binding, atomic single-use claim keyed on CAIP-2 + payment id, retention bound, rules for under/over-payment and refunds, and a declared finality boundary. While finality is pending but still reachable, settle must not deliver and must return an error. Lightning (`lnbtc`) is a live example: fresh BOLT11 invoice per challenge in `extra.invoice`, `upfront` only ([scheme_exact_lnbtc.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_lnbtc.md)).
- Runtime: SDKs register schemes per CAIP-2 pattern (`server.register("eip155:*", new ExactEvmScheme())`), so a custom scheme class can be registered without forking, but clients only pay entries for schemes they registered.

### 4.2 Extensions

Mechanics ([Extensions Overview](https://docs.x402.org/extensions/overview)): server declares `extensions[key] = { info, schema }` in `PaymentRequired`; client echoes into `PaymentPayload.extensions`; server-side `ResourceServerExtension` hooks (`enrichDeclaration`, `enrichPaymentRequiredResponse`, `enrichSettlementResponse`, scoped verify/settle hooks); facilitator-side `FacilitatorExtension`. Official inclusion in SDKs requires a maintainer-reviewed PR. Third-party namespaces are allowed if wire-compatible ([Third-Party Extensions](https://docs.x402.org/dev-tools/third-party-extensions)).

| Extension key | What it does |
| - | - |
| `bazaar` | discovery catalog; facilitator `/discovery/resources`, search; `EXTENSION-RESPONSES` status ([Bazaar](https://docs.x402.org/extensions/bazaar)) |
| `sign-in-with-x` | CAIP-122 wallet auth (SIWE / SIWS); `SIGN-IN-WITH-X` header; repeat access or auth-only routes (`accepts: []`); multi-chain `supportedChains` ([SIWX](https://docs.x402.org/extensions/sign-in-with-x)) |
| `payment-identifier` | client-chosen id (16-128 chars) for idempotent retries; bind to request fingerprint, `409` on mismatch ([Payment-Identifier](https://docs.x402.org/extensions/payment-identifier)) |
| `builder-code` | ERC-8021 attribution suffix in settlement calldata ([Builder Code](https://docs.x402.org/extensions/builder-code)) |
| `offer-receipt` | server-signed offers (on 402) and receipts (on 200), EIP-712 or JWS; TS only ([Offer & Receipt](https://docs.x402.org/extensions/offer-receipt)) |
| `eip2612GasSponsoring`, `erc20ApprovalGasSponsoring` | gasless Permit2 approval |

Spec folder also has `extension-auth-hints.md` and `http-message-signatures.md` ([specs/extensions](https://github.com/x402-foundation/x402/tree/main/specs/extensions)).

### 4.3 v1 vs v2 summary

| | v1 | v2 |
| - | - | - |
| Networks | strings (`base`, `solana-devnet`) | CAIP-2 |
| Amount field | `maxAmountRequired` | `amount` |
| Resource metadata | per-`accepts` entry | top-level `resource` object |
| Requirements transport | 402 JSON body | `PAYMENT-REQUIRED` header |
| Payload | `scheme` + `network` at top level | `accepted` echo of chosen requirements |
| Extensions | none | `extensions` on PaymentRequired / PaymentPayload / SettleResponse |
| Packages (TS) | `x402`, `x402-express`, `x402-axios`, … | `@x402/core`, `@x402/express`, `@x402/axios`, `@x402/evm`, … |

Facilitators can serve both versions during migration ([Migration guide](https://docs.x402.org/guides/migration-v1-to-v2)).

## 5. SDK integration

### 5.1 Server (provider)

Packages: `@x402/express`, `@x402/hono`, `@x402/next` (`paymentProxy`, `withX402`), `@x402/fastify`, `@x402/core`, mechanism packages `@x402/evm`, `@x402/svm`, `@x402/avm`, `@x402/near`, `@x402/stellar`, `@x402/aptos`, `@x402/tvm`, `@x402/xrpl`, …; Go `github.com/x402-foundation/x402/go/v2` (Gin, Echo, net/http); Python `x402[fastapi]`, `x402[flask]` ([Quickstart for Sellers](https://docs.x402.org/getting-started/quickstart-for-sellers)).

```ts
import { paymentMiddleware, x402ResourceServer } from "@x402/express";
import { HTTPFacilitatorClient } from "@x402/core/server";
import { ExactEvmScheme } from "@x402/evm/exact/server";
import { ExactSvmScheme } from "@x402/svm/exact/server";

const server = new x402ResourceServer(new HTTPFacilitatorClient({ url: FACILITATOR_URL }))
  .register("eip155:*", new ExactEvmScheme())
  .register("solana:*", new ExactSvmScheme());

app.use(paymentMiddleware({
  "GET /weather": {
    accepts: [
      { scheme: "exact", price: "$0.001", network: "eip155:8453", payTo: "0xSeller" },
      { scheme: "exact", price: "$0.001", network: "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp", payTo: "SellerSol" },
    ],
    description: "Weather data",
    mimeType: "application/json",
    extensions: { /* e.g. bazaar, payment-identifier */ },
  },
}, server));
```

Route option fields: `scheme`, `price` (dollar string or `{ amount, asset, extra }`), `network`, `payTo`, optional `maxTimeoutSeconds` (TS default 300 s, `x402ResourceServer.ts` L886), `extra`. `payTo` and `price` may be functions of the request context (`DynamicPayTo`, `dynamicPrice`; [SDK Features](https://docs.x402.org/sdk-features)). Hooks: `onProtectedRequest` (grant access, e.g. API key), `onBeforeVerify`, `onAfterSettle`, etc. ([Lifecycle Hooks](https://docs.x402.org/advanced-concepts/lifecycle-hooks)).

### 5.2 Client (buyer)

Packages: `@x402/fetch` (`wrapFetchWithPayment`), `@x402/axios` (`wrapAxiosWithPayment`), `@x402/core/client` (`x402Client`, `x402HTTPClient`), `@x402/mcp`; Go `x402http.WrapHTTPClientWithPayment`; Python `x402HttpxClient`, `x402_requests` ([Quickstart for Buyers](https://docs.x402.org/getting-started/quickstart-for-buyers)).

```ts
const client = x402Client.fromConfig({
  schemes: [
    { network: "eip155:*", client: new ExactEvmScheme(evmSigner) },
    { network: "near:*",   client: new ExactNearScheme(nearSigner) },
  ],
  spendControls: { maxAmountPerPayment: "$5", allowedAssets: [{ network: "eip155:8453", asset: "0xToken" }] },
});
const fetchWithPayment = wrapFetchWithPayment(fetch, client);
```

Wallet requirement: the buyer needs a signer for each network it wants to pay on (viem account, `@solana/kit` signer, NEAR full-access key, …) and must hold the advertised `asset` on that `network`. EVM Permit2 flows also need a Permit2 allowance or a gas-sponsoring extension.

## 6. Constraints that matter for a cross-chain gateway

| Topic | What x402 says |
| - | - |
| `payTo` vs `network` | `payTo` is an address on the same `network` as the payment. Every `exact` binding verifies a transfer of `asset` to `payTo` on that network (EVM `authorization.to` / `witness.to`, SVM ATA derived from `payTo`, NEAR `ft_transfer.receiver_id`). There is no field for a different destination chain or asset. |
| Settlement timing | Default `authorization` flow: verify → handler → settle → respond. The response is held until settle returns; failure becomes a 402. The facilitator waits for confirmation (EVM receipt, default wait 180 s in TS `toFacilitatorEvmSigner`; NEAR inner receipt `FINAL`). `upfront` settles before the handler. `batch-settlement` defers on-chain redemption. |
| Does the server wait for confirmation? | Yes in the reference SDKs. `settlement_pending` exists for confirmation timeouts but is treated as unresolved, not success. The HTTP transport defines no settlement-status endpoint. |
| `maxTimeoutSeconds` | Required on every entry. Maps to EIP-3009 `validBefore = now + maxTimeoutSeconds`, NEAR `max_block_height`, Stellar ledger expiry. TS default 300 s. HTTP facilitator client timeout default 90 s; MCP client caps at 600 s. |
| Exactness | `exact` requires the amount to match (EVM strict equality; SVM tolerates overpayment). No slippage concept. |
| Replay / nonce | Network primitive is authoritative: EIP-3009 32-byte nonce, Permit2 nonce, Solana blockhash plus 120 s `SettlementCache`, NEAR access-key nonce plus `max_block_height`. Client-submitted methods need an atomic single-use claim keyed by CAIP-2 + tx id. Application-level idempotency via `payment-identifier`. |
| Verify/serve binding | Server only accepts a payload whose `accepted` equals a requirement it advertises for that request. With a dynamic `payTo` (e.g. a fresh deposit address), the function must return the same value on the paid retry, or verification fails. (Inferred from `findMatchingRequirements` and `buildPaymentRequirementsFromOptions` in `x402ResourceServer.ts`; not stated in docs.) |
| Client defaults | Stock clients pay only default USD-pegged assets up to $1 unless configured, pay only schemes/networks they registered, and pick `accepts[0]` among survivors. |
| Refunds | `exact` is a push payment with no protocol refund; `upfront` failures leave the client charged ([scheme_exact.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact.md), [FAQ](https://docs.x402.org/faq)). `auth-capture` and `batch-settlement` define refunds. |

## 7. Multi-chain, cross-chain, swaps, "any token" in the docs

- **Multi-chain**: supported as *many single-chain options*. Servers list several `accepts` entries; clients register several networks; SIWX accepts several `supportedChains`. CAIP-2 is described as giving unambiguous cross-chain identification, meaning naming, not bridging ([Networks & Token Support](https://docs.x402.org/core-concepts/network-and-token-support)).
- **Any token**: within a chain only. Any ERC-20 via Permit2, any SPL/Token-2022, any NEP-141, etc. The payer must hold the exact `asset` the entry names.
- **Cross-chain / swaps / bridges**: no doc page, spec, or scheme covers cross-chain settlement or payer-side swaps. A repo-wide grep of `*.md` for cross-chain, bridge, swap, intents, 1Click finds only unrelated hits (CREATE2 addresses, Uniswap Permit2).
- Related signals:
  - Open issue [#4091](https://github.com/x402-foundation/x402/issues/4091) proposes a `swap` asset transfer method for `exact` on Stellar: payer spends XLM/EURC, a pinned and allowlisted contract swaps on an AMM and delivers exactly `amount` of `asset` to `payTo` in one transaction. It currently ships as a separate scheme `exact-fx` listed next to a plain `exact` entry so stock clients still pay. Same-chain and atomic; no maintainer answer yet.
  - FAQ: facilitators or third-party gateways can wrap x402 flows with on/off-ramps ([FAQ](https://docs.x402.org/faq)).
  - Intro lists proxy services that aggregate and resell APIs as a use case ([Introduction](https://docs.x402.org/introduction)).
  - The client-submitted family in `scheme_exact.md` explicitly allows a payment that starts asynchronous downstream settlement, with a declared finality stage.

## Implications for an any-asset gateway

Findings (yes/no, with source):

1. **A server can advertise N `accepts` entries across chains and assets: yes.** Each entry has its own `network`, `asset`, `amount`, `payTo`. ([spec v2 §5.1.2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md), [Quickstart for Sellers](https://docs.x402.org/getting-started/quickstart-for-sellers))
2. **The client chooses, not the server: yes.** TS SDK filters by registered schemes, spend controls, policies, then takes `accepts[0]`. Order the list by preference. (`x402Client.ts` L777-847)
3. **Stock clients pay arbitrary tokens out of the box: no.** Default spend controls allow only recognized USD-pegged assets and cap at $1. A buyer must opt in via `allowedAssets` or disable controls. ([Quickstart for Buyers](https://docs.x402.org/getting-started/quickstart-for-buyers))
4. **`payTo` can be on a different chain than `network`: no.** All `exact` bindings check the transfer to `payTo` on the payment's own network. ([scheme_exact_evm.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_evm.md), [scheme_exact_near.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_near.md), [scheme_exact_svm.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_svm.md))
5. **A gateway can put its own or an intent deposit address in `payTo` and stay inside plain `exact`: yes.** The x402 payment then settles to that address on the buyer's chain; the swap/bridge to the provider happens after and outside x402. Stock clients can pay this, subject to finding 3. The provider's `PAYMENT-RESPONSE` then proves payment to the deposit address, not receipt by the provider.
6. **Per-request `payTo` (fresh deposit address per quote) is supported: yes, with a caveat.** `DynamicPayTo` / `dynamicPrice` exist ([SDK Features](https://docs.x402.org/sdk-features)), but the paid retry must regenerate the same requirements or `accepted` will not match (inferred from `x402ResourceServer.ts`). Cache the quote by request or by `payment-identifier`.
7. **x402 can wait for cross-chain completion before responding: no, not in a supported way.** `/settle` is expected to reach finality synchronously (facilitator receipt wait, 90 s client timeout, `settlement_pending` treated as unresolved). Minute-scale bridge settlement does not fit inside one request. Options: count settlement at the deposit (finding 5), or use a client-submitted `upfront` method whose declared finality stage is the deposit. ([Facilitator](https://docs.x402.org/core-concepts/facilitator), [scheme_exact.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact.md))
8. **A custom third-party facilitator is allowed: yes.** Permissionless; must implement `/verify`, `/settle`, `/supported`. A gateway can be the facilitator for all buyer-side chains. ([Facilitators](https://docs.x402.org/dev-tools/facilitators), spec v2 §7)
9. **Facilitator pays gas on most chains: yes** (EVM, SVM, NEAR, Stellar); no on XRPL and Cardano. A gateway facilitator needs funded gas wallets per chain. ([Networks & Token Support](https://docs.x402.org/core-concepts/network-and-token-support))
10. **NEAR is a supported x402 network: yes** (`near:mainnet`, `exact`, NEP-141 via NEP-366 delegate action, TS `@x402/near`). ([scheme_exact_near.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_near.md))
11. **NEAR `exact` can deposit straight into an intents contract via `ft_transfer_call`: no.** Only a single `ft_transfer` is allowed, and `payTo` must be storage-registered for the token. A plain transfer to a registered deposit account is allowed. (same source)
12. **The docs mention NEAR Intents, swaps, or cross-chain settlement: no.** Closest is open issue [#4091](https://github.com/x402-foundation/x402/issues/4091) (same-chain atomic swap on Stellar). (repo grep, [Facilitators](https://docs.x402.org/dev-tools/facilitators))
13. **A payer-side swap can be expressed without a new scheme: yes, as a new `assetTransferMethod` of `exact` on a given network**, if seller-facing guarantees hold (exactly `amount` of `asset` to `payTo`). That is the shape proposed in #4091; it needs a spec PR per network and client support. ([scheme_exact.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact.md), [#4091](https://github.com/x402-foundation/x402/issues/4091))
14. **The spec has a slot for "client pays, async downstream settlement": yes**, the client-submitted (payment proof) method family with `upfront` flow, request binding, single-use claim, and declared finality. It requires writing a network binding and custom client support. ([scheme_exact.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact.md), [lnbtc example](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_lnbtc.md))
15. **A new scheme name can coexist with stock clients: yes.** Clients drop entries for schemes they have not registered, so list a custom entry (e.g. `exact-fx`) next to plain `exact` entries, as #4091's authors do. (`x402Client.ts` step 1, [#4091](https://github.com/x402-foundation/x402/issues/4091))
16. **Protocol-level gateway fee split: partial.** `extra.splits` on `exact` is specified only for Solana and must be advertised by the facilitator. ([scheme_exact.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact.md))
17. **Refund if the downstream swap fails: no protocol mechanism in `exact`.** The gateway must handle it (NEAR Intents refunds, own transfers), or use `auth-capture` (EVM only). ([FAQ](https://docs.x402.org/faq), [auth-capture spec](https://github.com/x402-foundation/x402/blob/main/specs/schemes/auth-capture/scheme_auth_capture.md))
18. **Replay protection beyond the chain primitive is needed for deposit-proof flows: yes.** Client-submitted methods must atomically claim a CAIP-2 + tx-id key. Use `payment-identifier` for retries. ([scheme_exact.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact.md), [Payment-Identifier](https://docs.x402.org/extensions/payment-identifier))

Bottom line: a gateway that advertises one plain `exact` entry per buyer chain, with a gateway-controlled or intent deposit address as `payTo`, fits inside x402 today and works with stock clients (subject to their spend controls). True "pay in X, provider receives Y on chain Z" semantics, where x402's settlement result means the provider was paid, cannot be expressed by `exact`. That needs either a new `assetTransferMethod` (atomic, same chain), a client-submitted proof method with declared finality, or a new scheme, each requiring custom client support.
